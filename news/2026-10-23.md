## 1. LLMs are making formal software verification feasible at a much larger scale

### Overview

Software has traditionally been filled with bugs that AI can now find and exploit.

Standard cyber defenses are no longer sufficient to guarantee safety against these attacks.

Researchers have demonstrated that large language models can perform formal software verification at a massive scale.

The research team collaborated with Theorem to verify code using the Claude model.

The author team includes Keane Lucas, Nicholas Carlini, Nickolai Zeldovich, and Jason Gross.

Claude verified security properties directly at the RISC-V assembly code level.

The project successfully analyzed more than 100 real-world open-source software libraries.

This marks the first large-scale effort to use AI for assembly-level formal verification on production code.

While writing proofs, Claude discovered long-standing bugs that escaped trillions of previous tests.

The researchers expect formal verification to become an essential part of secure software development.

### What happened

Researchers asked Claude to autonomously produce correctness proofs for 123 open-source libraries.

The experiment targeted 239 entry points drawn from Google's OSS-Fuzz initiative.

Claude proved that these programs will never crash under specified operational conditions.

The proofs confirmed normal exit without memory-safety errors or failed assertions for inputs under 64 MB.

The model autonomously patched the bugs it found during verification.

After patching code, Claude regenerated the specifications and proved the updated versions.

Claude generated roughly 180 million lines of Rocq proof code across several weeks.

A typical proof spanned approximately 600,000 lines of Rocq code.

These proofs verified binaries with a median size of 18,000 RISC-V instructions.

Traditional fuzz testers typically mutate inputs capped at 1 MB and rely on code coverage.

In contrast, Claude uncovered bugs requiring massive inputs or complex execution sequences.

Claude detected an out-of-bounds write from a decompressor counter underflow on rare 20 MB inputs.

It discovered an image decoder out-of-bounds read requiring a 64 MB input and 2 GB of memory.

It identified an out-of-bounds read triggered across two handles to the same file.

Claude also rediscovered CVE-2026-56132 in libexpat, which required deeply nested input.

The model even caught logic bugs that do not crash, such as unenforced file-loading restrictions.

### Why it matters

Even mature, heavily tested software deployed on billions of devices contains hidden flaws.

For example, the Linux kernel recently had over 1,000 vulnerabilities disclosed.

Frontier models are growing capable of chaining seemingly benign bugs into critical exploits.

Techniques are needed to eliminate bugs before they are exploited in the wild.

Formal verification proves that software mathematically complies with defined security rules.

Historically, writing proofs required years of effort and niche, specialized human skills.

Developing the seL4 operating system kernel took two person-years, but verifying it took 20 person-years.

High costs previously restricted formal verification to mission-critical applications like Airbus avionics code.

### Technical details

A major obstacle to formal verification has been creating comprehensive, unambiguous specifications.

Specifying simple formats like PNG decoders under RFC 2083 is clear, but general software is harder.

To address this, researchers converted preexisting fuzz test suites into formal mathematical specifications.

OSS-Fuzz provides entry points instrumented with AddressSanitizer to crash on improper memory access.

The generated specifications required that the fuzz test must never crash on inputs under 64 MB.

Proving this specification makes traditional fuzz testing of that entry point superfluous.

Assembly code was translated into mathematical models using Theorem's RISC-V and Linux process semantics.

Proofs assume single-threaded static binaries running with a fixed memory budget on Linux OS.

Generated proofs are validated mechanically by the Rocq proof checker.

Developers do not need to manually review the 180 million lines of generated proof code.

Trust is restricted to Rocq, the RISC-V instruction semantics, and the Linux process semantics.

Hardening these compact trusted components is far more tractable than auditing every line of application code.

### Industry impact

The cost of producing formal software proofs is falling as AI models improve.

Theorem is offering to run this automated verification pipeline for other open-source projects.

Theorem is also publishing a Claude skill to help developers verify their own codebases.

Amortized proof costs will drop further as security guarantees and formalization methods become standardized.

The authors explored additional tasks, including assessing the security of the zlib compression algorithm.

They also used formal methods to prove behavioral equivalence for a Rust-written Python interpreter.

Developers who previously abandoned formal verification using less capable models are urged to re-evaluate the technique.

### What to watch next

Researchers are publishing trusted components that were created for this project and not already public.

The team is releasing Claude's complete Rocq proofs for fuzz tests that required no patching.

Specifications for fuzz tests that Claude failed to prove are also being made public.

Future research aims to standardize semantics for additional CPU architectures beyond RISC-V.

Subsequent efforts will focus on expanding process semantics to include alternative operating systems.

What is not yet known is how soon these automated techniques will support multi-threaded binaries.

Observers will track whether developers adopt the Claude verification skill for ongoing production workflows.

## 4. PHP2Shell exploit bypasses protections designed to stop remote code execution

### Overview

A newly developed exploit demonstrates that memory protections cannot stop the PHP2Shell vulnerability.
Exploit intelligence firm VulnCheck confirmed that Address Space Layout Randomization on x86-64 servers can be bypassed.
VulnCheck warned that threat actors are actively spending time and tokens to exploit this flaw.
Attackers are also reportedly leveraging artificial intelligence to discover additional ways to attack vulnerable systems.
Security researchers urge organizations to patch immediately rather than relying on configuration defenses.

### What happened

On Wednesday, the PHP Foundation officially disclosed and released patches for the PHP2Shell vulnerability pair.
The security flaw pair consists of CVE-2026-109618 alongside CVE-2026-109619.
CVE-2026-109618 is a critical out-of-memory corruption vulnerability that leads to remote code execution in PHP.
On Thursday, reports surfaced that attackers had been abusing the security flaws days prior to official disclosure.
United Kingdom government websites proactively went dark as the crisis expanded.
VulnCheck researchers developed an exploit overnight targeting CVE-2026-109618.
The firm released the exploit exclusively to its Initial Access Intelligence customers.
VulnCheck believes this is the first known exploit achieving remote code execution on ASLR-enabled production systems.
Spencer McIntyre, director of exploit development at VulnCheck, called the achievement a significant advance.
Hundreds of PHP2Shell proof-of-concept repositories have appeared across GitHub.
McIntyre noted that very few public repositories contain legitimate, working exploits.

Background:
* PHP is a widely deployed open-source programming language used across global web infrastructure.
* The PHP Foundation maintains and coordinates development and security updates for the PHP project.
* VulnCheck is a cybersecurity firm specializing in vulnerability intelligence and exploit development.
* It is not yet known which specific UK government websites were taken offline.
* It is not yet known which threat actors exploited the flaw prior to disclosure.

### Why it matters

Address Space Layout Randomization has long served as a primary real-world barrier to memory corruption exploitation.
Security teams often assumed that ASLR would prevent PHP2Shell from enabling remote code execution on servers.
VulnCheck’s new exploit demonstrates that this major obstacle can now be overcome.
McIntyre explained that there is a significant difference between demonstrating a vulnerability and building a working exploit.
Developing an exploit that circumvents real-world security protections like ASLR is far from trivial.
McIntyre stated that the technical difficulty of exploiting a bug should not be confused with protection.
VulnCheck has not identified any other public or commercial exploit achieving this under production conditions.

Background:
* ASLR is a standard operating system defense against memory corruption attacks on modern hardware.
* Without memory addresses, exploit payloads typically crash target services rather than executing code.
* Artificial intelligence tools are increasingly used by security researchers and malicious actors alike.
* It is not yet known how many total servers globally remain vulnerable to PHP2Shell.

### Technical details

ASLR operates by randomly arranging the memory locations of a program's key data areas.
Scrambling data components live in memory prevents attackers from guessing target memory addresses correctly.
VulnCheck's exploit successfully bypasses ASLR on x86-64 servers.
The technique uses a confirmed memory leak chained directly into remote code execution.
The exploit was verified to function against systems running PHP version 8.4.26.
The attack operates successfully even with PHP's recommended display_errors=off production configuration.
VulnCheck confirmed that the underlying bypass technique also works on ARM64 systems.
However, remote code execution is not currently functional on ARM-based hardware.

Background:
* The display_errors directive determines whether PHP outputs error messages directly to end users.
* Production environments standardly disable display_errors to hide sensitive diagnostic information.
* Information leaks allow attackers to calculate memory layouts and defeat randomization protections.
* x86-64 and ARM64 utilize differing instruction sets and memory architectures.
* It is not yet known if researchers will achieve functional RCE on ARM64 architectures.

The proactive shutdown of UK government websites indicates severe real-world alarm.
Evidence showing pre-disclosure exploitation suggests threat actors prioritized weaponizing the bug early.
Threat actors are actively utilizing artificial intelligence to uncover additional attack avenues.

## 5. LiteLLM release pipeline hacked to distribute info-stealer malware

### Overview

A supply-chain attack has targeted the widely used open-source LiteLLM project.

Threat actors compromised the project's release pipeline on October 21.

The attackers pushed malicious packages to PyPI and the Docker registry.

The compromise distributed infostealer malware affecting version 1.107.0.

The payload is designed to steal credentials, secrets, and environment variables.

All PyPI wheels for version 1.107.0 were impacted across operating systems.

Targeted platforms include Windows, Linux, and macOS systems.

LiteLLM maintainers issued a post-mortem detailing the incident.

### What happened

On October 21, attackers pushed compromised version 1.107.0 releases.

The poisoned packages were sent to both PyPI and the Docker registry.

The maintainer stated that the version contained compiled malware.

The malware steals credentials and loads remote-code execution tools.

Security companies detected the attack six minutes after package publication.

Researchers analyzed the malicious installation artifacts immediately.

The attacker did not alter the core LiteLLM application code.

Instead, the attacker modified the package installation files.

Three malicious files were added to the environment's Python library directory.

These files were named cook.pth, cook.py, and sitecustomize.py.

### Why it matters

LiteLLM is an open-source Python SDK and AI gateway.
