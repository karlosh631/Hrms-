## 1. PostgreSQL 19

### Overview

- PostgreSQL 19 has been detailed with numerous performance upgrades and system enhancements.
- The release introduces new commands, extended statistical tools, and altered security defaults.
- Database administrators can utilize a built-in REPACK command for online table reorganization.
- JIT compilation is now disabled by default due to unreliable optimizer cost calculations.
- Upgrading to PostgreSQL 19 requires a dump and restore, pg_upgrade, or logical replication.
- The update introduces key performance gains in join processing and background worker management.
- Storage compression defaults have transitioned to lz4 for improved efficiency.
- Standby databases now support read-your-writes consistency using a new WAIT command.
- Security has been updated by removing unfixably insecure RADIUS over UDP support.
- System monitoring expands with several new statistical views and process metrics.

### What happened

- PostgreSQL 19 introduces a REPACK command to reclaim disk space and reorganize tables.
- Using REPACK CONCURRENTLY allows repacking without blocking active table reads and writes.
- Two new extensions, pg_plan_advice and pg_stash_advice, provide control over query planner decisions.
- Logical replication can now be enabled without restarting the server when wal_level is set to replica.
- Autovacuum operations now support parallel execution across table indexes.
- A new scoring system has been added to prioritize autovacuum tasks across databases.
- Automatic scaling has been added for the number of I/O worker processes.
- The io_workers server variable was removed and replaced by four new background worker control variables.
- Standard_conforming_strings is now permanently forced to be enabled on the database server.
- Insecure RADIUS over UDP authentication support has been completely removed from PostgreSQL.
- Database, role, and tablespace names can no longer contain carriage returns or line feeds.
- Default index opclasses for inet and cidr data types shifted from btree_gist to GiST.
- The default password expiration warning period was set to seven days via a new server variable.
- MD5 password authentication now issues a warning following successful login attempts.
- The obsolete MULE_INTERNAL text encoding has been completely removed from PostgreSQL 19.

### Why it matters

- Automatic I/O worker scaling improves overall database scalability under heavy workloads.
- Disabling JIT by default prevents unexpected performance degradation on standard queries.
- Sites executing large analytical queries must now manually enable JIT compilation when beneficial.
- Read-your-writes consistency via the WAIT command ensures standby nodes serve up-to-date query results.
- The shift to lz4 as the default TOAST compression algorithm improves data storage efficiency.
- Shared cost-based vacuum delays ensure parallel autovacuum workers stay strictly within configured limits.
- Preventing control characters in object names eliminates specific security vulnerabilities during operations.
- Eliminating broken btree_gist index classes prevents queries from returning incomplete or missing rows.
- Forcing standard_conforming_strings prevents string literal interpretation errors across client applications.
- System administrators receive clearer operational visibility through expanded system statistics views.
- Simplified constant folding in the optimizer speeds up boolean logic and conditional query execution.
- Quicker foreign-key constraint checks reduce overall latency during data operations.

### Technical details

- The server now features io_min_workers, io_max_workers, io_worker_idle_timeout, and io_worker_launch_interval variables.
- SIMD CPU instructions now accelerate COPY FROM operations processing text and CSV data formats.
- NOTIFY signals now target only backends listening for specific notification events.
- Query table scans can now mark pages as all-visible directly inside the visibility map.
- TID Range Scans can now be parallelized across multiple process workers.
- Aggregate processing can occur prior to join execution to reduce processed row counts.
- Optimizer enhancements convert eligible NOT IN and LEFT JOIN queries into ANTI JOINs.
- Extended statistics are now supported on virtual generated columns.
- New administration functions include pg_restore_extended_stats() and pg_clear_extended_stats().
- System view pg_stat_progress_repack monitors progress for REPACK, CLUSTER, and VACUUM FULL tasks.
- System view pg_stat_autovacuum_scores provides per-table autovacuum operational details.
- System view pg_stat_lock and function pg_stat_get_lock() deliver per-lock-type statistical tracking.
- System view pg_stat_recovery reports current recovery process states and progress.
- Default max_locks_per_transaction has been increased from 64 to 128 locks.
- System columns are no longer permitted within COPY FROM ... WHERE clause conditions.
- Calling json_array() with zero rows returned now produces an empty JSON array.
- Transactions now propagate READ ONLY and DEFERRABLE statuses directly to postgres_fdw sessions.
- Full text search and pg_trgm now utilize the database locale provider for character parsing.

### Industry impact

- Upgrades from earlier major releases require running pg_upgrade, pg_dumpall, or logical replication.
- Databases using deprecated btree_gist inet or cidr indexes will block pg_upgrade operations until modified.
- Pre-PostgreSQL 19 dumps created with standard_conforming_strings set to off will fail to restore.
- Upgraded databases using custom locale providers require reindexing full text search and pg_trgm indexes.
- Index reindexing is also recommended for databases using fuzzystrmatch non-ASCII text functions.
- Migration of databases using MULE_INTERNAL requires a full dump and restore into a supported encoding.
- Administrators relying on MD5 password warnings can control notifications via md5_password_warnings.
- Database clusters using carriage returns in role or database names must rename them before upgrading.

### What to watch next

- Administrators should verify whether their analytical workloads require re-enabling JIT execution manually.
- Storage configurations should be evaluated to benefit from the new lz4 TOAST default setting.
- Operational scripts should be updated to monitor the new pg_stat_autovacuum_scores view.
- Replication monitoring setups need to update metrics to track sync_table_error_count instead of sync_error_count.
- System administrators must adjust lock allocation settings to accommodate the updated max_locks_per_transaction baseline.
- Further details on background worker configuration options can be reviewed in Section E.1.3.1.2.
- General instructions on major release data migration remain detailed in Section 18.6.

## 2. OpenSSL: Buffer overflow in EVP_EncodeBlock() (CVE-2026-121481, CVSS 9.8)

### Overview
Welcome to today's daily IT news digest for November 20, 2026.
We are covering a critical vulnerability report coming from Hacker News regarding OpenSSL.
The discussion centers around a buffer overflow issue found within the EVP_EncodeBlock() function.
This security flaw has been designated as CVE-2026-121481.
The vulnerability carries a severe Common Vulnerability Scoring System rating of CVSS 9.8.
The OpenSSL Security Response Team has requested a public fix for the issue.
Meanwhile, the official advisory for this specific vulnerability remains pending.

### What happened
The reported security flaw is a buffer overflow bug located inside the EVP_EncodeBlock() function.
Initially, developers considered returning -1 for invalid inputs to resolve the problem.
Such invalid inputs include NULL input or output buffers and negative lengths.
They also considered lengths where the encoded size does not fit into a standard integer.
This proposed initial approach was similar to wolfSSL's compatibility layer for EVP_EncodeBlock().
However, extensive discussions among contributors raised concerns about negative return values.
Reviewers worried third-party callers might cast the return value to size_t without checking it.
Others pointed out that returning -1 could break existing third-party applications.
Alternative suggestions included returning 0 or utilizing OPENSSL_assert().
Critics argued that returning a magic value appearing like success introduces dead code.
Following robust feedback, the pull request was adjusted to focus purely on the CVE fix.
Developers implemented OPENSSL_assert() for inputs that previously triggered undefined behavior.
Additional adjustments preserved all existing well-defined behavior for empty inputs and buffers.
Tests were added in test/base64_dec_avx2_test.c to properly cover the new behavior.
Documentation updates were prepared in doc/man3/EVP_EncodeInit.pod.
Developers also tracked an internal function issue by referencing issue number #33812.

### Why it matters
Vulnerabilities in cryptographic libraries like OpenSSL pose major risks across the technology sector.
A CVSS 9.8 rating indicates an exceptionally high severity level for this buffer overflow.
Improper handling of invalid inputs can lead to application crashes or unpredictable memory states.
Changes to fundamental return values can inadvertently impact external third-party software integrations.
Balancing rapid CVE remediation with API stability requires careful engineering discussions.
Discussions in this case highlighted the friction between changing error behaviors and maintaining backwards compatibility.
Preventing undefined behavior without breaking existing software callers is a delicate task.

### Technical details
The vulnerability affects the EVP_EncodeBlock() function in OpenSSL.
Exploitation can be achieved from the command line by passing a large -proxy_pass value.
This can be executed through openssl s_client when targeting systems like GOST.
The large password must be supplied using an environment variable to prevent command line length limits.
The underlying pattern of CVE-2026-121481 closely mirrors that of CVE-2021-23840.
Mitigation strategies shifted from returning -1 to using OPENSSL_assert() for invalid inputs.
This avoids forcing third-party callers to manage unexpected negative return codes.
The base64encode() function in http_client.c also contained an incorrect length check rejecting only len > INT_MAX.
AVX2 code paths required safeguards to prevent undefined behavior when source pointers are NULL.
An issue number comment #33812 was added to guide future internal function refactoring.

### Industry impact
OpenSSL is a foundational security library utilized across countless enterprise and open-source systems.
Discussions regarding this bug reveal internal development and review practices within the OpenSSL project.
Comparison with wolfSSL highlights cross-library differences in handling compatibility layers and error codes.
Contributors actively debated whether to deprecate broken APIs or strictly patch immediate CVE vectors.
Such security disclosures push developers to evaluate how callers handle legacy C function return contracts.

### What what to watch next
Watch for the official OpenSSL security advisory to be published regarding CVE-2026-121481.
Monitor downstream Linux distributions and software vendors for upcoming OpenSSL patch releases.
Track follow-up work associated with issue number #33812 for internal function improvements.
Observe whether third-party projects report any integration challenges with the updated assertion checks.
Background: OpenSSL is widely used for secure communications, and maintaining its robust API contract is critical.
It is not yet known precisely when the official advisory will drop or which specific software versions will adopt the patch first.
